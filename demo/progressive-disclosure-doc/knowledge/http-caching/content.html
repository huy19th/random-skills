An HTTP cache stores responses to reuse them for later requests, cutting latency and bandwidth.

A fresh response is used right away; a stale one must be validated with the origin server before use.

Servers control caching mainly through the Cache-Control header.

How a cache works

  • Reusing a stored response is the default behavior, unless something forbids it

    So the caching rules focus on preventing a cache from storing or reusing responses wrongly, not on forcing a cache to store any response.

  • There are 2 kinds of cache: shared cache (CDN, proxy) and private cache (browser)

    The distinction matters because some directives only apply to shared caches, e.g. s-maxage and private.

  • A cache picks a stored response by its cache key, at minimum the request method and URI

    In practice many caches only cache GET requests, so they use the URI alone as the cache key.

    The Vary response header adds some request headers to the cache key, e.g. Vary: Accept-Language to store the English and French versions separately.

Fresh and stale

  • A response is fresh while its age has not exceeded its freshness lifetime; otherwise it is stale 
    response_is_fresh = (freshness_lifetime > current_age)

    Age counts from when the origin server generated the response, or from its last successful validation.

  • The freshness lifetime is computed by an order of precedence, using the first rule that matches
    1. Shared cache and s-maxage present: use that value.
    2. max-age present: use that value.
    3. Expires header present: Expires minus Date.
    4. None of these: the cache may estimate one (heuristic), see the next point.
  • When the server sets no lifetime, the cache may estimate one, typically 10% of the time since Last-Modified

    Example: a file last modified 10 days ago → the cache may treat the response as fresh for about 1 day.

    Consequence: omitting Cache-Control does not mean the response is not cached. Inference

Validation

  • Once a response is stale, the cache sends a conditional request to the origin server to ask whether the stored response is still usable. This is called validation

    The conditional request usually carries If-None-Match (compares ETags) or If-Modified-Since (compares times). Inference

  • The origin answers 304 Not Modified → the cache updates the metadata and reuses the stored response without downloading the content again

Key Cache-Control directives

  • max-age=N: the response becomes stale after N seconds
  • s-maxage=N: like max-age but only for a shared cache, and it overrides both max-age and Expires
  • no-cache does not mean "do not cache": the response is still stored, but must be validated before every use

    Often confused with no-store. To store nothing at all, use no-store.

    The qualified form, e.g. no-cache="Set-Cookie", is poorly supported by caches; it is often treated as an unqualified no-cache.

  • no-store: the cache must not store any part of the request or the response

    Do not rely on no-store for security: a malicious or compromised cache may ignore it.

  • private: a shared cache must not store the response; a private cache still may
  • must-revalidate: once stale, the response must be validated; if the origin is unreachable, return an error instead of the stale response

    The error code to use is 504 Gateway Timeout.

    Only use it when serving outdated data breaks the business logic, e.g. financial transactions.

  • When directives conflict, e.g. both max-age and no-cache: the most restrictive one wins
  • Static files with a hash in their name (e.g. app.3f9a.js) should get a long max-age Inference

    When the content changes, the file name changes, so the URL and the cache key change too. An old response is never reused by mistake.

Open questions

  • RFC 9111 does not define a specific heuristic algorithm. What ratio do popular browsers actually use? Needs another source.
  • The immutable and stale-while-revalidate directives are not covered by the current source.

Terms

fresh

A response still within its lifetime: used right away without asking the origin server again.

A response is fresh while its age has not exceeded its freshness lifetime.

stale

A response past its lifetime: usually must be validated before reuse.

A response is stale once its age has exceeded its freshness lifetime.

age

Time elapsed since the origin generated the response, or since its last successful validation.

Each successful validation resets the age.

freshness lifetime

How long a response counts as fresh, measured from when the origin generated it.

Taken from s-maxage, max-age, Expires, or estimated by the cache.

cache key

The information a cache uses to pick a stored response, at minimum the method and URI.

Can also include the headers listed in Vary.

validation

The cache asks the origin server whether a stored response is still usable.

Also called revalidation. The origin answers 304 if the stored response is still usable, or sends a new response.
